# 31 — Pixel Art: Adventure Map, Heroes, Units

Replace procedural SVG glyphs with generated pixel art, incrementally, using the PixelLab API. The game must remain fully playable at every commit — art lands in small batches behind a fallback. Rendering-only: no rules, state-model, or spec changes anywhere in this milestone. Judgment calls → DECISIONS.md; do not ask. Batch reflections → `ASSETS_LOG.md` (new file, described below).

## 0. Ground rules

- **Sizes are law.** Adventure terrain tiles 32×32. Heroes 32×48, 8 directions. Combat units use a separate 128×128 visual canvas; mounted or 2-hex units may use 192×128, and 3-hex units 256×128. Tactical footprint and visual overhang are deliberately independent.
- **Visual canvas ≠ footprint (the H2 rule).** A map object's sprite canvas is any multiple of 32 wide (≥ its footprint width) × any height, **bottom-anchored to its footprint**. The footprint (per S03, as amended by doc 32: castles 3×2, mines 2×1) remains the only gameplay truth — passability, entrance, aggro, fog all unchanged; everything above it is overhang that may occlude tiles behind. Use it: an obelisk-class 1×1 object can be 32×64 or taller; a 2×1 mine maybe 64×80; the 3×2 castles should rise to 96×128-ish with their towers. Partial occlusion of a hero standing behind a tall object is accepted, H2-style — it is what makes the map read as a place.
- **Entrances are drawn where they are.** Any object with an entrance tile must draw its visual entrance (gate, door, mine mouth) ON that tile: castle gates dead-center of the bottom edge (entrance = bottom-center tile), mine mouths over the entrance tile per map data. The sprite must never suggest walking in anywhere the game won't allow.
- **Native resolution only.** Generate at final pixel size. Never upscale or downscale art. Rendering scales by integers only (×1/×2/×3) via one global pixel-scale constant, `image-rendering: pixelated` everywhere sprites appear.
- **One style.** HoMM2-era storybook pixel art: warm, painterly, crisp, readable. Light comes from the screen lower-right / map southeast and cast shadows travel toward the screen upper-left / map northwest, with no exceptions. Never grimdark. Faction materials, palettes, and silhouette languages per S08_CANON are binding; the Assimilation Laws (mundane first read, rationed strangeness) apply to art exactly as they apply to text.
- **One camera (the anti-isometric law).** The adventure map is oblique, HoMM-style: objects face the camera front-on with a slight overhead tilt (~30°); ground contact is a **horizontal band**, never an isometric diamond. NO isometric perspective anywhere — state the camera explicitly in every prompt and reject any candidate with a diamond base or corner-on view, regardless of how good it looks otherwise. Check the endpoint's view/perspective parameters against the OpenAPI spec and pin the correct values in the job files.
- **Palette coherence.** Terrain and objects must read as one game. Once a batch's terrain is approved, its tiles become mandatory reference images (or explicit palette anchors) for every object generated to stand on it; every batch's reflection step compares new assets against shipped ones in-game, and palette drift is a rejection reason.
- **Scale is stated, then checked.** Every prompt states the object's intended tile coverage ("fills 3 tiles wide, ~4 tall"); every batch review includes a side-by-side of the new assets against a shipped reference object at ×2. A dwelling is roughly half a castle's height, a mountain range taller than both — relative scale errors are a rejection reason.
- **Prompts are source code.** `assets/prompts.md` records, per shipped asset: exact prompt, endpoint, parameters, and reference images used. It must be sufficient for a future agent to regenerate or extend any category in-style. Update it in the same commit as the asset.
- **No baked player colors, flags via overlay.** Sprites never contain owner colors or flags. Every capturable/flaggable object kind (castles, mines, dwellings, Rich Vein, Lighthouse, anything with an owner in state) gets a mandatory `flagAnchor: {x, y}` in its manifest entry — a pixel position on the sprite where the renderer plants an owner flag. The flag itself: generate ONE small pixel-art pennant sprite (~10×16) with its cloth in a reserved key color (pure magenta `#ff00ff`); at load, the UI produces per-player recolored variants by pixel-swapping the key color (one-time offscreen processing — this does not violate the no-canvas-rendering stance). Neutral/unowned: a grey variant or no flag, matching current behavior. Fallback if recoloring fights us: a plain player-colored SVG pennant at the same anchor — accept and log it.

## 1. Wiring: manifest + fallback (build this first, Batch 0)

- `assets/manifest.ts`: maps content/kind ids → `{file, w, h, anchor, flagAnchor?}`. A renderable thing whose id is in the manifest draws the sprite; anything absent keeps its current SVG glyph unchanged. The game is complete and playable at any coverage level.
- **Painter's-algorithm rendering:** all sprites on the adventure map (objects, heroes, tall decorations) render sorted by anchor row, then column — lower rows draw over higher rows, so overhangs occlude naturally. Build this into the Batch-0 renderer along with the flag-overlay and pennant-recolor machinery, before any assets exist (test with the current glyphs given fake tall canvases).
- Loader preloads manifest images; a missing/broken file logs a warning and falls back to the glyph (never a broken-image icon).
- `npm run assets-check`: validates every manifest entry — file exists, PNG dimensions match the declared size, width is a multiple of 32 and ≥ the owner's footprint width, `flagAnchor` present and within canvas for every ownable object kind. Wire into `pretest`. Also print a coverage report (sprited vs glyph count per category).
- Enumerate the asset worklist from the **actual content data and all authored maps** (`src/content/`, map files) — not from the design docs. Anything rendered on the adventure screen today is in scope for Phases A–C.

**API:** docs at `https://api.pixellab.ai/v2/llms.txt` (OpenAPI: `https://api.pixellab.ai/v2/openapi.json`); official SDKs exist (`pip install pixellab`, or the JS/TS client) — build the script on one of them rather than raw HTTP. Generation endpoints are async (job id + poll `GET /background-jobs/{job_id}`); the script owns the polling. Endpoint mapping (verify parameters against the OpenAPI spec, don't guess):

- Terrain (Phase A): `POST /create-tileset` generates top-down **Wang tilesets** — evaluate it in A1 first, since it may hand us terrain-to-terrain transitions nearly free; fall back to per-tile generation via `create-image-pixflux`/`pixen` if tileset output doesn't fit the 32px grid or style. This milestone originally deferred transition wiring; doc 36 records the later generated sets and current integration boundary.
- Map objects (Phases A props + B): evaluate `POST /generate-image-v2` first for larger flagship objects because it returns automatically background-removed native-size variations and avoided the dedicated endpoint's stock ground plates in the landscape probe. `POST /map-objects` remains the dedicated transparent-object fallback; pin `view` because its default is `high top-down`.
- Heroes (Phase C): `POST /create-character-with-8-directions` (or `create-character-v3`, 8 rotations) to get all facings in one call; `POST /generate-8-rotations-v3` as the alternative when rotating an already-approved canonical facing. Pick per observed quality, log the choice.
- Battle units (Phase D): character endpoints for a single facing; `create-image-bitforge` accepts style reference images — that's the mechanism for the flagship-as-reference protocol in §6.
- `POST /enhance-*-prompt` endpoints exist; may be used during style-lock, but the FINAL prompt recorded in prompts.md is always the literal one sent.

**Generation is scripted, not conversational (token discipline):** build a generation CLI in Batch 0 (`scripts/pixelgen`) and drive ALL production generation through it — do not call the PixelLab MCP/API interactively inside the agent loop. The workflow:

- A batch is a **job file** (JSON/TS in `assets/jobs/`): a list of requests — asset id, prompt, endpoint (incl. the 8-direction endpoint), size, candidate count, reference images, output paths. Job files are committed; together with prompts.md they are the regeneration record.
- The script executes the whole job: API calls, polling/waiting, retries with backoff, writing PNGs to predictable paths, and a **one-line-per-asset summary** (`ok bannerman 3 candidates 64x64` / `FAIL water: <reason>`). Nonzero exit on any failure. It must be quiet: no streamed API responses, no base64, no progress chatter to stdout.
- The agent runs the script, waits for completion, and reads only the summary — and stderr only when the exit code is nonzero. Results are inspected by *looking at the outputs* (open the candidate sheet or the game screenshot), never by reading API response payloads.
- Candidate review support: the script also emits a `candidates.html` contact sheet per job (all candidates at ×2 on light/dark ground) so picking winners is one look, not N tool calls.
- Direct MCP/API calls are permitted only for quick one-off probes (testing a new endpoint's behavior, a single style experiment); anything generating shippable assets goes through a job file. If a one-off probe produces a keeper, backfill the job file.

**Batch discipline (every batch, all phases):** write/update the job file → run `pixelgen` (2–3 candidates per asset, keep the best) → compose in-game (run the game, screenshot the relevant screen) → **reflect** (see §2) → fix prompts and rerun the job for failures → wire manifest entries → `assets-check` + smoke green → commit (assets + job file + manifest + prompts.md + ASSETS_LOG.md entry). Batches are small: ~4–10 assets. One commit per batch, always shippable.

## 2. The reflection step (mandatory, per batch)

After composing each batch in-game, write a short critique in `ASSETS_LOG.md` before committing: what reads well, what fails, and what prompt changes the next batch inherits. Known failure classes from the proof-of-concept run — check for these explicitly:

- **Baked directional lighting/gradients in tileable art.** The sample water tile was light at top, dark at bottom — tiled vertically it banded. Rule: terrain tiles must be lighting-uniform across the tile; verify every terrain candidate by composing a 3×3 block of itself and inspecting the seams and the overall field. Texture detail yes, per-tile gradient no.
- **Context baked into standalone objects.** The sample mine implied a mountainside behind it. Rule: map objects sit on transparent backgrounds, self-contained, valid on ANY terrain — no cast environment, no horizon, at most a small neutral ground shadow.
- **Baked base plates.** A later sample run produced buildings on their own grass skirts (flowers, pebbles, a diamond of lawn) — the objects looked like miniatures plopped onto the board. Rule: no ground plate of any kind; the object's ground contact is a clean horizontal edge that meets our terrain tiles directly. Prompt for it ("no base, no ground, transparent below the walls") and reject violators.
- **Isometric drift.** The same run came back isometric on a top-down map. See the camera law in §0 — this is the single most likely silent failure of map-object endpoints; check every candidate.
- Others to watch: flags/banners baked into ownable buildings (the overlay owns flags — prompt them out: "no flags, no banners"); inconsistent light direction between batches; outline weight drift; palette drift from faction laws; objects reading as a different scale than their neighbors (compare against previously shipped assets in-game, not in isolation).

## 3. Phase A — Terrain (three layers, per S03 / archived doc 28)

The terrain system has three layers — gameplay terrain, skin, decoration — plus authored obstacle props. Art maps onto it directly: one base-tile set per (terrain, skin) pair actually used by the authored maps; decoration sprites composite over base tiles; props are standalone objects.

- **Batch A1 — the Border Marches core:** Meadow, Deepwood, Mountain (whichever skins the maps use), Water. Each base tile with 2–3 interchangeable variants (same palette/lighting, minor texture differences) to break repetition; the renderer picks a variant deterministically from tile coordinates. This batch alone re-skins most of Border Marches — it is the style-lock batch; iterate hardest here.
  - **The forest experiment (decide in A1, log the verdict):** flat forest-terrain texture looks like disconnected broccoli patches; H2 forests work because overlapping tall tree sprites form a canopy. Deepwood terrain stays passable, so trees here are *decorations*, not obstacles. Build both candidates and compare screenshots: (a) tall tree-clump decorations (1–2 tiles high, y-sorted, heroes walk partially behind canopy) scattered by the existing seeded decoration system, with a readability mitigation — decorations drop to ~40% opacity when a hero or interactive object is within 1 tile behind them; (b) tall trees only on the border tiles of each forest region, flat texture inside. Pick the winner, apply the same verdict to Mosswold later. Mountains get the same treatment uncontroversially: a few tall overlapping mountain props composed into ranges rather than per-tile self-contained texture (mountains are impassable, so no readability cost).
- **Batch A2 — overlays:** Road segments (straight/corner/crossing as the maps need; composite over any terrain) and the Seam (subtle, wrong-colored ground — it must read as "the land changes its mind," not as an effect).
- **Batch A3 — remaining gameplay terrains** as used by authored maps: Barrowfield, Mosswold, Ashsteppe, Lacquer Flats, The Hush, Mire. Each carries its identity per S03's catalog (Lacquer's glossy grain, Barrowfield's pale grass) under the Assimilation Laws — mundane first read.
- **Batch A4 — decorations and obstacle props** for the skins in use: decorations are small transparent sprites composited by the existing seeded scatter (passable, never interactive); props (boulder, old oak, dolmen, the Spool, the Block…) are standalone 1×1 or 2×1 objects following the §2 standalone rule. Do not touch the authored/seeded boundary — art only.
- Acceptance per batch: affected maps visible in-game with no seams, no banding, no checkerboard artifacts at ×1, ×2, ×3. Terrain-to-terrain transition tiles (shorelines etc.) were out of scope for this milestone; the later native transition implementation and continuation point are consolidated in doc 36. Log it.

## 4. Phase B — Adventure map objects

Batched by kind, roughly in map-prominence order (derive the exact lists from map data — includes doc-29 objects where present):

- **B1** — resource piles (gold, timber, iron, essence) and treasure chest.
- **B2** — mines: gold mine, timber camp, iron mine, essence spring (2×1 footprint per doc 32, taller canvas welcome, mouth drawn over the entrance tile), Rich Vein. First capturables — the flag overlay must be visibly correct here before proceeding.
- **B3** — castles: one per faction, 3×2 footprint per doc 32 with towers rising well above it, **gate drawn dead-center of the bottom edge** on the entrance tile, faction material/palette per S08. These are the flagship assets — spend candidates freely. Neutral towns (29) reuse the pattern.
- Phase B does not start until doc 32 (footprint shrink) has landed — sprite proportions depend on it.
- **B4** — shrines (4 schools), barrow-mound, waystation, Mana Spring if present in content.
- **B5** — dwellings placed on the authored maps (generic-but-faction-flavored).
- **B6** — creative landmarks placed on the maps (Tinker's Cart, Monastery, Gloaming Ring, Storyteller's Fire, Chrysalis Pool, Half-Built Bridge, Hedge School, Reliquary Cairn, Toll Gate, Omen Stone, puzzle-lock map presences, Masque Ring, and whatever else map data names — check, don't assume).
- Guardian stacks on the map keep their current glyph until units exist (Phase D); log it.

## 5. Phase C — Heroes (8 orientations)

- One rider sprite per faction **class** (Banneret, Guildmaster, Chandler, Broodspeaker, Crone, Ashrider), not per named hero. 32×48. Mounts/locomotion per faction identity (S08): Banneret on horse with pennant; Crone on besom; Ashrider on steppe horse; Guildmaster in a Guild cart or on a hobby-horse construct; Chandler as a drifting light-bearer; Broodspeaker on a chitin mount. Judgment calls on the fun ones — log them.
- **Use the dedicated 8-direction endpoints** (see §1 endpoint mapping) so all 8 facings come from one generation, consistent by construction. Verify all 8 in-game by walking a hero in a circle; the renderer picks the facing from movement direction (last-moved direction persists at rest; default facing S).
- One batch per faction, or two factions per batch once the prompt template is proven. First faction (Hearthguard) is the template-setter: iterate until right, then reuse the structure.

## 6. Phase D — Battle units

- 128×128, side view facing right (renderer mirrors for the other side), feet on a baseline ~8px above bottom. Mounted and 2-hex silhouettes may use 192×128; 3-hex silhouettes use 256×128. These are visual canvases, not occupied-hex declarations: standards, wings, mounts, and weapons may overhang adjoining hexes. Static sprites — no animation frames this milestone.
- One faction per batch, in order: Hearthguard, Wound-Wrights, then the rest; neutral-culture units and sea creatures last.
- **Reference-image protocol (resolve the open question empirically in the first two batches):** for each faction, first generate the flagship unit (the faction's most identity-dense mid-tier — e.g. Bannerman, Marionette) standalone. Then generate the second unit twice: once prompt-only, once passing the flagship as a style/reference image via the API's reference mechanism. Compare in-game, log the verdict in ASSETS_LOG.md, and use the winning method for the rest of the faction (re-evaluate once more when a faction's material language differs wildly, e.g. Vespiary chitin after Hearthguard cloth). Silhouette law check per batch: all of a faction's shipped units rendered as solid-black silhouettes must be mutually distinguishable and attributable to their faction (S08's test, now enforceable).
- Wire into the combat screen: sprite replaces the circle token; stack count badge, morale arc, counter pips, and selection highlights all render OVER the sprite unchanged.
- Battlefield terrain art (palettes, obstacle prop sprites per S03's battlefield templates) is explicitly deferred; battle props share art direction with their adventure-terrain siblings when they do arrive.

## 7. Acceptance

- Every commit in the milestone: `assets-check`, map lint, full test suite, and browser smoke green. Renderer and asset-manifest changes only.
- End state: all authored maps fully sprited (terrain layers + objects), six hero sprites × 8 facings walking correctly, all faction battle units sprited, coverage report showing what remains on glyphs (icons, portraits, battle terrain — explicitly deferred).
- `prompts.md` + `ASSETS_LOG.md` together tell the full story: a future agent can regenerate any asset, extend any category, and knows every style decision and why.
